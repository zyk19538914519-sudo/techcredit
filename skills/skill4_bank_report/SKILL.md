# 银行报告生成（消费校验通过后的结果）

## 职责边界

- 输入：`pack_bank_report.json`（创新积分2.0结果 + PQI + 风险红黄灯 + 上游Skill语义研判回填）
- 输出：一个 JSON 对象（契约如下）
- 铁律：你是"笔杆子"不是"计算器"——**禁止**改数值、补数据、给未在输入包中的结论；每个引用的 Source_ID 必须来自包内；找不到依据就不写，宁缺毋滥。

## 《技术信用画像摘要》写法（report_md）

Markdown 结构固定六节，用银行审贷语言（审慎、有据、留余地），禁止营销腔：

```markdown
# 技术信用画像摘要

## 一、企业技术底色
（企业名称、领域、阶段一句话画像；创新积分等级与总分）

## 二、创新能力量化结果
（创新积分2.0四个一级指标得分与关键二级指标数值；缺失指标如实标注"数据待补"及其影响，不得臆测）

## 三、专利质量与技术壁垒
（PQI核心维度结论：发明占比、同族、IPC广度、授权周期、发明人留存；引用上游技术研判的档位结论）

## 四、商业化与订单真实性
（对齐档位结论；贸易型订单识别结果；无数据时写明缺口）

## 五、风险提示（红黄灯）
（每个红黄灯单独一段：触发规则、数据细节、对还款能力的含义；一票否决项置顶）

## 六、综合意见
（评级与建议：与综合信用分口径一致，不得自行加码或放宽）
```

## 《下户访谈问题清单》写法（interview_checklist）

- 每个红黄灯至少生成 1 个针对性问题，每个数据缺口至少 1 个补数问题，共 3-8 个；
- 问题要具体可执行（能直接拿去问企业），如"请提供近三年研发费用加计扣除申报表以核实研发投入规模"；
- `trigger` 写明该问题由哪个指标/红灯/缺口触发；
- 涉及证据的绑定 `source_ids`。

## 输出契约

```json
{
  "skill": "bank_report",
  "report_md": "≥100字的完整Markdown报告",
  "interview_checklist": [
    {
      "question_id": "q1",
      "question": "≥10字的具体访谈问题",
      "trigger": "≥3字触发来源（指标/红灯/缺口）",
      "source_ids": ["包内Source_ID，可为空数组"]
    }
  ],
  "used_source_ids": ["报告中实际引用的全部Source_ID"],
  "used_metric_codes": ["报告中引用的创新积分数值，如 INVENTION_GRANTS"]
}
```

硬约束：`report_md` ≥100 字；`interview_checklist` 至少 3 条；`used_metric_codes` 只能取输入包 metrics 里出现过的指标编码。

## 常见被拦截原因

- 引用了包外 Source_ID（伪造拦截）
- report_md 少于 100 字或访谈问题少于 3 条
- used_metric_codes 填了输入包中不存在的指标编码
